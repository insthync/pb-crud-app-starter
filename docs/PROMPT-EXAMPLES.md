# คลัง prompt สำหรับสร้างเว็บจาก starter

ใช้คู่กับ [คู่มือ Bootstrap](BOOTSTRAP-GUIDE.md) ตัวอย่างเว็บด้านล่างเป็นงานที่จะพัฒนาเพิ่ม ไม่ใช่ฟีเจอร์ที่มีอยู่แล้ว แทนค่าที่อยู่ใน `[วงเล็บ]` ก่อนส่ง และเปิดแชตในโฟลเดอร์ repo ใหม่

## A. ให้ ChatGPT ช่วยแปลงไอเดียเป็นข้อกำหนด

แนบ README ของ starter หรือวางเนื้อหาที่เกี่ยวข้องพร้อม prompt นี้:

```text
ฉันจะสร้างเว็บโดยใช้ pb-crud-app-starter
Stack: HTML/CSS/JavaScript + PocketBase + SQLite
มี login, registration, viewer/editor/admin และ CRUD ตัวอย่างอยู่แล้ว

เว็บที่อยากได้: [อธิบายปัญหา]
ผู้ใช้งาน: [ใครใช้ จำนวนคนโดยประมาณ]
ตัวอย่างงานจริงหนึ่งรอบ: [เริ่มอย่างไร ทำอะไร จบอย่างไร]
ข้อมูลที่คิดว่าต้องเก็บ: [รายการข้อมูล]

ช่วยสรุปข้อกำหนดรุ่นแรก ประกอบด้วย:
1. หน้าจอและการทำงานของแต่ละหน้า
2. ตารางข้อมูล ฟิลด์ ชนิดข้อมูล และฟิลด์บังคับ
3. สิทธิ์แต่ละ role และขอบเขตการเห็นข้อมูล
4. สถานะและกฎการเปลี่ยนสถานะ
5. เกณฑ์ตรวจรับพร้อมตัวอย่างผ่าน/ไม่ผ่าน
6. ขอบเขตที่ยังไม่ทำในรุ่นแรก

ถามเฉพาะข้อมูลที่มีผลต่อการออกแบบ ถ้าเสนอสมมติฐานให้ระบุชัด
ท้ายสุดเขียน prompt ส่งต่อให้ Codex พัฒนาใน repo ใหม่
```

## B. ให้ Codex เตรียมโปรเจคที่ clone มาแล้ว

```text
โฟลเดอร์ปัจจุบันเป็น repo ใหม่ที่สร้างจาก pb-crud-app-starter
ชื่อแอปใหม่: [ชื่อแอป]

อ่าน AGENTS.md, README.md และ docs/INDEX.md
อ่านเอกสารที่เกี่ยวข้อง ตรวจ git status, remote และ implementation
ปรับชื่อแอปใน config, HTML และเอกสารให้ตรงกัน
เก็บระบบสมาชิก หน้า admin และสิทธิ์เดิมไว้
อัปเดต docs/HANDOFF.md เป็นสถานะของแอปใหม่นี้
ระบุให้ชัดว่าตอนนี้มีอะไรแล้วและอะไรยังเป็นงานต่อไป

ตรวจ syntax และลิงก์เอกสาร อัปเดต asset version หากแก้ frontend
ทดสอบด้วยฐานข้อมูลชั่วคราว ไม่ใช้ข้อมูลจริงหรือ credentials ใน repo
ยังไม่ deploy หรือ push จนกว่าฉันจะสั่ง
```

## C. ตัวอย่างครบ: ระบบแจ้งซ่อมภายในทีม

ตัวอย่างนี้ให้สมาชิกในทีมอ่านงานร่วมกันตามค่าเริ่มต้นของ starter ส่วนการอนุญาตให้ viewer เปิดงานเป็นการขยายสิทธิ์เฉพาะ collection ใหม่ จึงต้องทดสอบ API เพิ่ม

```text
พัฒนา repo นี้จาก pb-crud-app-starter เป็นเว็บชื่อ team-maintenance
อ่าน AGENTS.md และ docs ก่อน ตรวจโค้ดจริงและ git status

เป้าหมาย: ทีมงานแจ้งปัญหาอุปกรณ์และติดตามการซ่อมผ่านมือถือ
คง HTML/CSS/JavaScript + PocketBase + SQLite และ UI ภาษาไทย
คง login, registration และหน้า admin จัดการสมาชิก

หน้าจอ:
- รายการแจ้งซ่อม ค้นหาหัวข้อ/สถานที่ กรองสถานะและความเร่งด่วน แบ่งหน้า
- ฟอร์มสร้างงาน และหน้ารายละเอียด/อัปเดตงาน
- สรุปจำนวนงานตามสถานะ โดยนับจากข้อมูลทั้งหมดที่ผู้ใช้มีสิทธิ์เห็น

ข้อมูล maintenance_requests:
- title: ข้อความบังคับ ไม่เกิน 200 ตัวอักษร
- location: ข้อความบังคับ ไม่เกิน 200 ตัวอักษร
- description: ข้อความบังคับ ไม่เกิน 4000 ตัวอักษร
- priority: low / normal / urgent ค่าเริ่มต้น normal
- status: new / in_progress / resolved ค่าเริ่มต้น new
- requester: relation ไป users กำหนดจากผู้ที่เข้าสู่ระบบบน server
- assignee: relation ไป users ไม่บังคับ ต้องเป็น active editor/admin
- resolution: ข้อความผลการแก้ไข ไม่เกิน 4000 ตัวอักษร
- created / updated: วันที่ระบบกำหนด

สิทธิ์:
- Guest อ่านหรือเขียนงานไม่ได้
- active viewer/editor/admin อ่านงานทั้งทีมได้
- viewer สร้างงานได้ โดย server บังคับ requester เป็นตนเอง
  status=new และยังไม่มี assignee/resolution
- viewer แก้ไขได้เฉพาะ title/location/description/priority
  ของงานตนเองที่ยังเป็น new ลบงานหรือเปลี่ยน requester ไม่ได้
- editor/admin อัปเดตงาน รับผิดชอบงาน และเปลี่ยนสถานะได้
  requester ต้องคงเดิม และรุ่นแรกไม่ให้ลบงานเพื่อรักษาประวัติรายการ
- เฉพาะ admin จัดการสมาชิก ตามขอบเขตเดิมของ starter

กฎ:
- new → in_progress → resolved; รุ่นแรกยังไม่รองรับเปิดงานที่ปิดแล้ว
- resolved ต้องมี resolution ที่ไม่ใช่ข้อความว่าง
- บังคับสิทธิ์ที่ API rules และตรวจ business rules ฝั่ง server
- UI ซ่อน/ปิดปุ่มให้สอดคล้องกับสิทธิ์ แต่ต้องยิง API ข้ามไม่ได้

ขอบเขตรุ่นแรก: ยังไม่แนบไฟล์ ไม่ส่งอีเมล ไม่แยกองค์กร
พิจารณาปิด public registration ก่อนใช้งานจริงภายในทีม

ทำ migration ใหม่ เปลี่ยนหน้ารายการตัวอย่างเป็นหน้าของระบบนี้
ปรับ tests ให้ตรงกับ schema ใหม่ ทดสอบ guest/viewer/editor/admin
ทดสอบการปลอม requester และการแก้งานคนอื่นโดย viewer
ตรวจ desktop/mobile ด้วยข้อมูลสมมติและฐานข้อมูลชั่วคราว
อัปเดต README และ HANDOFF แล้วสรุปวิธีรันกับผลทดสอบ
```

## D. ตัวอย่างครบ: ระบบยืมคืนอุปกรณ์

```text
ใช้ repo นี้ที่สร้างจาก pb-crud-app-starter พัฒนา equipment-borrowing
อ่าน AGENTS.md และ docs ตรวจ implementation กับ git status ก่อนเริ่ม
คง stack เดิม UI ภาษาไทย login และหน้า admin

ผู้ใช้เป็นเจ้าหน้าที่ทีมเดียว ข้อมูลอ่านร่วมกันหลังเข้าสู่ระบบ
viewer อ่านข้อมูลได้ editor/admin จัดการยืมคืนได้
admin จัดการสมาชิกตามสิทธิ์เดิม

ข้อมูล:
- equipment: code ไม่ซ้ำ, name, category, total_quantity จำนวนเต็มบวก,
  active, description
- loans: equipment relation, borrower_name, quantity จำนวนเต็มบวก,
  borrowed_date, due_date, returned_at, status borrowed/returned,
  created_by relation ที่ server กำหนดจากผู้เข้าสู่ระบบ, created/updated

หน้าจอ:
- ทะเบียนอุปกรณ์ พร้อมจำนวนทั้งหมด จำนวนค้างยืม และจำนวนคงเหลือ
- เพิ่ม/แก้ไขอุปกรณ์เฉพาะ editor/admin
- ฟอร์มยืมเลือกอุปกรณ์ที่ active และจำนวนที่ต้องการ
- รายการยืม ค้นหาผู้ยืม กรองสถานะ/เกินกำหนด และแบ่งหน้า
- ปุ่มคืนอุปกรณ์พร้อมยืนยัน แล้วแสดงวันเวลาที่ server บันทึก

กฎสำคัญ:
- จำนวนคงเหลือ = จำนวนทั้งหมด - จำนวนในรายการ borrowed
- ห้ามยืมเกินคงเหลือ แม้สองคนส่งคำขอพร้อมกัน
- ตรวจและบันทึกการยืมอย่างเป็นอะตอมฝั่ง server
- ห้ามลดจำนวนอุปกรณ์ทั้งหมดต่ำกว่าจำนวนที่ยังค้างยืม
- คืนได้เต็มจำนวนต่อรายการเท่านั้น ห้ามคืนซ้ำ
- วันกำหนดคืนต้องไม่ก่อนวันยืม
- เมื่อบันทึกยืมแล้วห้ามแก้อุปกรณ์ จำนวน หรือผู้สร้างย้อนหลัง
- ไม่ลบรายการยืมและอุปกรณ์ที่ถูกอ้างอิง ให้ปิดใช้งานอุปกรณ์แทน
- ป้องกันการเรียก generic API ข้ามกฎเดียวกับ custom endpoint

รุ่นแรกไม่รองรับคืนบางส่วน การจองล่วงหน้า ไฟล์แนบ หรือหลายองค์กร
สร้าง migrations และปรับ tests รวมการยืมพร้อมกัน/คืนซ้ำ/สิทธิ์ทั้งสาม role
ใช้ฐานข้อมูลชั่วคราว ตรวจ desktop/mobile และอัปเดต README/HANDOFF
```

## E. เพิ่มฟิลด์ให้เว็บที่ทำงานอยู่แล้ว

```text
เพิ่มฟิลด์ category ให้รายการงานของโปรเจคนี้
อ่าน AGENTS.md, HANDOFF และ schema ปัจจุบันก่อน
ค่าเป็น general / equipment / document ค่าเริ่มต้น general

ทำ migration ใหม่โดยรองรับรายการเดิมที่ไม่มีค่า
เพิ่มในฟอร์ม สร้าง/แก้ไข/ดูรายละเอียด และตัวกรองรายการ
ตรวจว่าค่าบันทึกกลับมาในฟอร์มได้และ server ปฏิเสธค่าที่ไม่อยู่ในตัวเลือก
ปรับ tests ที่เกี่ยวข้องและอัปเดตเอกสารกับ asset version
ทดสอบด้วยข้อมูลสมมติในฐานข้อมูลชั่วคราว
อย่าแก้ฐานข้อมูลใช้งานจริงหรือเขียนทับ migration ที่ใช้ไปแล้ว
```

## F. ปรับหน้าตาตามภาพอ้างอิง

แนบภาพที่ต้องการพร้อมข้อความนี้:

```text
ปรับหน้าตาเว็บนี้ตามภาพอ้างอิงที่แนบ
ใช้โครงสร้างสี ระยะห่าง และลำดับเนื้อหาเป็นแนวทาง
คงฟังก์ชัน CRUD, login และ admin ที่มีอยู่
UI ภาษาไทย ใช้ HTML/CSS/JavaScript เดิม

ตรวจ desktop และมือถือ 390px ให้ไม่มีเนื้อหาล้นแนวนอน
ปุ่ม ฟอร์ม และ dialog ใช้คีย์บอร์ดได้ มี label และ focus ที่มองเห็น
ใช้ข้อมูลสมมติในการตรวจภาพ ไม่แสดง credentials หรือข้อมูลจริง
อัปเดต asset version และ HANDOFF พร้อมสรุปหน้าจอที่ตรวจแล้ว
```

## G. แก้บั๊กอย่างมีข้อมูล

```text
ช่วยแก้บั๊กในโปรเจคนี้ อ่าน AGENTS.md และ HANDOFF ก่อน
หน้าที่พบ: [หน้า]
บัญชีทดสอบมี role: [viewer/editor/admin]
ขั้นตอนทำซ้ำ: [1 → 2 → 3]
ผลที่คาดหวัง: [ผล]
ผลที่เกิดจริง: [อาการหรือข้อความ error ที่ตัดข้อมูลลับออกแล้ว]

หาสาเหตุจาก implementation และทำซ้ำในฐานข้อมูลชั่วคราว
แก้ส่วนที่จำเป็นและตรวจ regression ของ flow ที่ได้รับผลกระทบ
ถ้าเกี่ยวกับสิทธิ์ให้ทดสอบ API โดยตรงด้วย
สรุปสาเหตุ สิ่งที่แก้ วิธีทดสอบ และอัปเดต HANDOFF
```

## H. ปิดงานและกลับมาทำต่อ

ก่อนจบช่วงงาน:

```text
ตรวจ diff ของงานรอบนี้และผลทดสอบ
อัปเดต docs/HANDOFF.md ให้ระบุสิ่งที่เสร็จ ข้อจำกัด และงานถัดไป
ตรวจว่าไม่มี credentials, pb_data, binary หรือข้อมูลจริงอยู่ในไฟล์ที่จะ commit
สรุปวิธีเปิดใช้งานและไฟล์สำคัญที่เปลี่ยน
```

เมื่อเริ่มแชตใหม่:

```text
ทำงานต่อใน repo นี้ อ่าน AGENTS.md, docs/INDEX.md และ docs/HANDOFF.md
ตรวจ git status และ implementation เพื่อยืนยันสถานะจริง
งานถัดไปคือ [รายละเอียด]
รักษางานที่มีอยู่ ทดสอบตามผลกระทบ และอัปเดต HANDOFF เมื่อเสร็จ
```

## เกณฑ์ตรวจ prompt ก่อนส่ง

- มีเป้าหมายและผู้ใช้งานชัดเจน
- ระบุข้อมูล ฟิลด์บังคับ และชนิดข้อมูล
- ระบุว่าใครเห็นข้อมูลของใครได้ ไม่บอกแค่ชื่อ role
- ระบุกฎธุรกิจเป็นตัวอย่างที่ทดสอบผ่าน/ไม่ผ่านได้
- แยกสิ่งที่ต้องทำตอนนี้กับสิ่งที่ยังไม่ทำ
- สั่งปรับทั้ง schema, UI, API และ tests ตามที่ได้รับผลกระทบ
- ไม่ใส่รหัสผ่านหรือข้อมูลจริงลงใน prompt

รูปแบบ prompt ในหน้านี้เป็นตัวอย่างที่ออกแบบสำหรับ repository นี้ ส่วนพฤติกรรมการอ่านคำแนะนำของ Codex อ้างอิง [OpenAI: AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
